# 開発フロー

## 全体の流れ

1. Issueを立てる
2. ブランチを切る
3. 実装する
4. PRを出す
5. セルフレビューする
6. マージ・Issueクローズ

## 1. Issue

作業を始める前に必ずIssueを立てる。
Issueテンプレートに従い、**スコープ（やること／やらないこと）** と **完了条件** を必ず記入する。

追加要望が発生した場合も、その場で着手せずIssueとして登録する。

## 2. ブランチ

### 命名規則

種別/issue番号-内容

例:
- feature/12-add-task-form
- fix/15-login-error
- docs/3-update-readme

### 種別

| 種別 | 用途 |
|---|---|
| feature | 機能追加 |
| fix | バグ修正 |
| docs | ドキュメント |
| refactor | リファクタリング |

### 構成

main + 作業ブランチの2階層。developブランチは設けない。
mainへの直接pushは禁止（ブランチ保護ルールで制限）。

## 3. 実装

AIに実装を依頼する場合は、対象のIssue本文をそのまま渡す。
Issueに書かれていない仕様をAIに判断させない。
判断が必要になった時点で、一度手を止めてIssueを更新する。

## 4. コミット

### 形式（Conventional Commits）

<種別>: <内容>

例:
- feat: タスク作成フォームを追加
- fix: ログイン時のバリデーションエラーを修正
- docs: 要件定義書を更新

### 種別

feat / fix / docs / refactor / test / chore

## 5. PR

PRテンプレートに従って記入する。
本文に `Closes #12` と書くことで、マージ時にIssueが自動でクローズされる。

## 6. セルフレビュー

マージ前に、PRのセルフレビュー項目をすべて確認する。

**「AIが書いたコードを1行ずつ読んで理解した」にチェックが付けられない場合、マージしない。**

理解できていないコードをmainに入れないことが、このプロジェクトの最重要ルール。

## 7. マージ

- マージ方式：Squash and merge
- マージ後、作業ブランチは削除する
